# HarmonyOS 多推理框架 NPU 统一接入方案汇报

> 汇报版 | 2026-09-01

## 0. 一页结论

### 0.1 当前问题

第三方框架目前可以调用华为NPU，但MNN、ncnn、LiteRT、ONNX Runtime分别维护算子映射、分图、Layout、编译、缓存和执行。同一NPU在不同框架下的正确性、性能和可观测性不一致。

Demo给出了直接证据：

| 现象 | 数据 | 说明 |
|---|---:|---|
| 小图逐算子委托 | MNN USER_1为102.66 ms，原生NNRT为51.57 ms | 多次提交、同步和CPU/NPU边界让性能下降约一倍 |
| 整图语义转换错误 | USER_0早期IoU仅0.328 | 图能编译不等于Layout、Axis、Flatten和Softmax语义正确 |
| 修复后整图性能成立 | NPU 49.64 ms，USER_0 49.90 ms | MNN整图路径可以接近原生NPU，端到端只差约0.5% |
| 业务链路瓶颈不可见 | ROI预处理约31 ms，模型执行约9 ms | 只提高NPU频率无法解决完整链路问题 |

**问题不是NPU算力不足，而是多框架适配、正确性、性能优化和资源调度责任过于分散。**

### 0.2 要解决的问题

统一方案需要解决四件事：

1. **接得上**：MNN、ncnn、LiteRT、ORT使用稳定接口接入麒麟NPU；
2. **跑得对**：统一Shape、Layout、Axis、量化和算子语义，正确性先于性能；
3. **跑得快**：以连续大子图为单位执行，减少小图提交、数据搬运和重复编译；
4. **调得好**：统一上报工作负载和业务SLA，为CPU、NPU、DDR、DMA和内存调度提供可信信息。

### 0.3 方案

    MNN       ncnn       LiteRT       ONNX Runtime
     │         │           │               │
    薄插件    薄插件      Delegate          EP
     └───────────────┬─────────────────────┘
                     │
        Huawei Framework Adapter API
     图语义 / 能力 / 分图 / 内存 / 资源提示
                     │
             NNRt Graph Runtime
    校验 / 编译 / Cache / 执行 / 调度 / Profiling
                     │
              CANN Kit / Kirin NPU

一句话概括：

> **框架负责提供标准图和业务目标，华为Runtime统一负责NPU最优执行与系统资源协同。**

### 0.4 核心价值

| 价值 | 当前方式 | 统一后 |
|---|---|---|
| **生态效率（重点）** | **每个框架重复开发和维护NPU后端** | **一套底层优化同时覆盖MNN、ncnn、LiteRT和ORT** |
| **系统调度（重点）** | **系统看到负载升高后才被动调频** | **提前获得计算量、DDR字节、deadline和阶段信息，联合调度CPU/NPU/DDR** |
| 性能 | USER_1逐算子路径比原生NPU慢约一倍 | 大子图执行，目标与NNRT稳定态差距不超过10% |
| 正确性 | 各框架分别处理Layout、Axis和量化，图能运行但可能结果错误 | 统一IR语义、固定Fixture和中间Tensor定位形成发布门禁 |
| 开发体验 | 应用难以确认NPU命中、回退和拷贝 | 一份报告说明子图、fallback、Cache、内存和性能损失 |

最终价值不是“多一个SDK”，而是：

- 把第三方框架性能上限拉近系统原生路径；
- 把单框架修复变成多框架共享能力；
- 把不可解释的NPU调用变成可验证、可调度的系统工作负载；
- 为相机、直播、会议和大模型持续推理降低CPU、DDR和功耗成本。

### 0.5 主要风险

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 抽象层自身增加开销 | 多一层封装反而变慢 | 稳定C ABI、热路径不复制、异步Fence和Buffer复用 |
| 统一IR语义不完整 | 图能编译但输出错误 | 显式Layout/Axis/Quantization、语义版本化、Fixture门禁 |
| 分图成本模型不准 | NPU子图比CPU/GPU更慢 | 实机数据校准、收益阈值、可解释回退和规则覆盖 |
| 应用虚报高优先级 | NPU长期高频，影响公平性与功耗 | 应用只报SLA，系统校验限幅，禁止直接控制绝对频率 |
| 框架和系统版本演进 | 插件失效或静默fallback | LTS版本矩阵、Feature Bit、自动回归和Cache完整失效规则 |

方案边界：不保证所有模型都进入NPU，不替代框架CPU/GPU后端，不向三方应用开放直接调频权限。

### 0.6 需要决策

1. 是否建设统一Huawei Framework Adapter，而不是继续按框架分别修补；
2. HFA作为NNRt新接口，还是NNRt之上的独立Kit；
3. 第一阶段是否以MNN为样板，同时定义可扩展到LiteRT/ncnn的稳定C ABI；
4. 是否将资源信息预埋纳入第一阶段，先观测、后用户态策略、最后内核闭环；
5. 是否以“正确性门禁、与NNRT差距不超过10%、无静默fallback”作为首批验收标准。

以下章节展开说明问题、架构、关键设计和落地计划。

## 1. 背景

当前 MNN、ncnn、LiteRT、ONNX Runtime 等第三方推理框架需要分别适配华为 NPU。每个框架独立实现算子映射、分图、Tensor Layout、模型编译、缓存和执行，导致接入成本高，正确性和性能表现不一致。

现有 Demo 已验证两类典型问题：

- **逐算子委托性能差**：MNN `USER_1` 只把部分卷积逐个交给 HiAI，固定图片下完整帧平均耗时从原生 NNRT 的 `51.57 ms` 增加到 `102.66 ms`，NPU 完成中断频率达到 `3.72 倍`。
- **整图适配正确性难保证，但修复后性能潜力成立**：MNN `USER_0` 曾因三维输出布局、ConvertTensor、Flatten 和 Softmax 语义错误得到 `IoU=0.328`；修复后固定输入达到 `IoU=0.954`、68点最大误差 `0.00168`。两轮后摄合并结果为原生NPU `49.64 ms`、MNN-U0 `49.90 ms`，端到端只差约 `0.5%`。

结论：当前问题不是 NPU 算力不足，而是不同框架各自实现 NPU 适配，优化和正确性责任过于分散。

## 2. 当前架构问题

```text
MNN       ncnn       LiteRT       ONNX Runtime
 │         │           │               │
独立后端  独立适配层   独立Delegate   独立Execution Provider
 │         │           │               │
各自实现算子映射、分图、Layout、Cache、执行
 └───────────────┬─────────────────────┘
           HiAI / NNRt / CANN
                  │
               Kirin NPU
```

主要问题：

1. 单算子或小子图频繁提交，CPU/NPU 往返过多。
2. 同一算子在不同框架中重复适配，结果和性能不一致。
3. Layout、Axis、Broadcast 和量化语义容易转换错误。
4. 编译缓存和内存管理无法跨框架复用。
5. 应用只能看到“NPU 后端已选择”，看不到实际下沉比例和回退原因。

## 3. 优化方案

借鉴 Google LiteRT Delegate 的可插拔思路，但建设面向多个框架的统一抽象层：

```text
MNN       ncnn       LiteRT       ONNX Runtime
 │         │           │               │
薄插件    薄插件      Delegate          EP
 └───────────────┬─────────────────────┘
                 │
    Huawei Framework Adapter API
       统一图、能力查询和内存协议
                 │
         NNRt Graph Runtime
   分图 / 编译 / Cache / 调度 / Profiling
                 │
              CANN Kit
                 │
             Kirin NPU
```

核心原则：

- 每个框架只保留一个轻量插件，不再自行实现完整 NPU 编译逻辑。
- 华为统一负责算子能力、图划分、成本评估、编译缓存、内存和性能分析。
- NPU 以连续大子图为执行单位，避免逐卷积提交。
- 不支持算子继续由框架 CPU/GPU 执行，但回退必须可见、可解释。
- 正确性校验先于性能发布。

## 4. 核心设计

### 4.1 统一框架接口

提供稳定的 C ABI，覆盖：

```text
设备和能力查询
完整图分析
分图方案生成
NPU 子图编译
编译结果加载和缓存
Tensor 与共享内存绑定
同步/异步执行
Profiling 和回退原因
```

### 4.2 基于收益的分图

不能采用“算子支持就下沉”的方式，应综合计算：

```text
下沉收益
= CPU/GPU执行时间
- NPU计算时间
- 数据拷贝
- Layout转换
- 提交与同步
- 摊销后的编译成本
```

只有总收益为正、子图计算量足够时才进入 NPU。

### 4.3 统一正确性契约

统一 IR 必须明确表达：

- 逻辑 Shape 和物理 Shape；
- Tensor Layout 和通道 Packing；
- Axis、Broadcast 和动态维度；
- 数据类型与量化参数；
- 算子语义版本。

每个设备和框架组合必须通过固定输入 Fixture，与 CPU Reference 对齐后才能发布。

### 4.4 内存与缓存

- 支持 Shared Memory、Native Buffer、DMA-BUF 和 NPU Buffer 导入。
- 通过 Layout 协商减少 Host 中转和格式转换。
- 编译缓存同时绑定模型、Shape、SoC、驱动、CANN 和算子库版本。
- 稳态执行不重复编译，不重复创建 Tensor 和工作区。

### 4.5 可观测性

统一输出：

- NPU 节点占比和子图数量；
- CPU/GPU 回退节点及原因；
- 编译时间和 Cache 命中；
- 边界拷贝字节数；
- Layout 转换次数和耗时；
- 子图排队、执行和 Fence 等待时间；
- P50/P95/P99、功耗和频点。

### 4.6 资源信息预埋与系统调度闭环

统一抽象层还应成为推理工作负载向系统资源管理器提供可信信息的入口。框架只上报事实和SLA，系统统一决定CPU、NPU、DDR、DMA和内存策略，三方应用不能直接指定硬件最高频。

建议预埋三类信息：

| 类别 | 关键字段 | 系统价值 |
|---|---|---|
| 图静态特征 | FLOPs、权重、Tensor峰值、输入输出字节、子图数、CPU回退、计算/访存类型 | 预测NPU、DDR和内存需求 |
| 请求意图 | deadline、period、优先级、前后台、是否可丢帧、功耗模式 | 支持实时性和多应用仲裁 |
| 阶段与反馈 | 预处理、上传、排队、执行、回读、后处理、实际耗时和频点 | 提前供给并形成自适应闭环 |

由此可以支持：

1. **CPU提前供给**：预处理和NPU提交线程在关键窗口获得合适CPU簇和短时boost；
2. **NPU/DDR联合调频**：Cube密集图优先NPU，访存密集图优先DDR，避免无效拉满；
3. **连续子图频率保持**：人脸图与关键点图属于同一请求时，避免图间反复升降频；
4. **Deadline感知调度**：前台实时请求优先，过期且可丢帧的请求直接取消；
5. **DMA与内存复用**：根据Tensor大小、生命周期和生产者提前准备共享Buffer与IOMMU映射；
6. **Fallback联动**：CPU回退时同步调整CPU/NPU资源，而不是继续维持错误投票。

当前Demo最值得先预埋的是：`ROI预处理开始/结束`、`NPU提交/完成`、输入输出字节数、Face与Landmark连续图关系，以及 `deadline=50 ms / period=125 ms / droppable=true` 等请求属性。

## 5. 预期收益

### 对应用开发者

- 继续使用 MNN、ncnn、LiteRT 等原有接口。
- 只需选择 Huawei NPU Backend，不直接理解 CANN 和驱动。
- 同一模型可在 NPU、CPU、GPU 之间可靠回退。

### 对框架生态

- 减少重复的算子和 NPU 后端开发。
- 华为底层优化可以同时覆盖多个框架。
- 统一兼容矩阵和测试标准。

### 对性能

- 减少 NPU 提交和 CPU/NPU 边界。
- 提高中间 Tensor 驻留和算子融合机会。
- 降低 CPU 占用、DDR 搬运和长尾。
- 根据图的计算/访存特征和业务deadline进行CPU、NPU、DDR联合资源供给。
- 目标是第三方框架稳定态性能与 MindSpore Lite/NNRT 差距控制在 `10%` 以内。

## 6. 落地计划

| 阶段 | 主要工作 | 目标 |
| --- | --- | --- |
| 阶段 0 | 统一 Trace、固定 Fixture、后端命中报告、资源字段只观测 | 能解释是否使用NPU、为什么慢、需要什么资源 |
| 阶段 1 | 定义最小Adapter API，改造MNN插件，用户态策略服务读取资源提示 | 人脸/关键点正确，性能接近NNRT，验证CPU/NPU/DDR提前供给 |
| 阶段 2 | 统一分图、缓存、共享内存，支持 LiteRT/ncnn | 多框架复用同一套优化 |
| 阶段 3 | 异步执行、动态Shape、内核资源闭环、多模型调度、ORT | 支撑相机、直播、语音和大模型场景 |

## 7. 建议优先决策

1. 统一抽象层是作为 NNRt 新接口，还是独立的 Framework Adapter Kit。
2. 统一图格式复用 MindIR/NNRt IR，还是定义稳定交换 IR。
3. 第一批官方支持 MNN 和 LiteRT，还是同时覆盖 ncnn。
4. 编译缓存是否允许跨应用系统级复用。
5. CANN 高级能力以什么范围向三方框架开放。

## 8. 最终建议

建议采用：

> **多框架薄插件 + 统一 Framework Adapter API + NNRt/CANN 高性能 Runtime**

这不是简单增加一层接口包装，而是把分散在各框架中的正确性和性能优化能力收敛到华为统一维护，使第三方框架能够稳定、高效地使用麒麟 NPU。

完整设计见：[HarmonyOS 多推理框架 NPU 统一抽象层设计](harmonyos_multi_framework_npu_abstraction_design.md)。
